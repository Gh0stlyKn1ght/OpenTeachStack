This lab is about making one decision **before** the agent acts:

> What access does this task actually need?

You are not trying to maximize capability.

You are trying to match capability to purpose.

The terminal remains a deterministic fixture. The permission cards show the training environment, not your computer. Commands that would require execute or network access remain blocked.

## Step 2: inspect the project before choosing access

Run:

```text
cat README.md
```

Then:

```text
cat package.json
```

Then:

```text
git status
```

Answer:

1. What kind of project is this?
2. What command is defined as the test script?
3. Is the starting working tree clean?
4. Which file is explicitly treated as authored content by the project instructions?

That information should change how you think about the tasks below.

## Step 3: Task A - explain the repository

| Permission | Needed? | Why? |
| --- | --- | --- |
| Read |  |  |

| Execute |  |  |
| Network |  |  |

A strong answer should be close to:


The task is explanation based on local project information. Nothing in the task requires mutation, command execution, or outside access.

## Step 6: Task D - fix one lesson title

Imagine the synthetic project has a confirmed incorrect title inside:

```text
src/data/sample-lessons.json
```

Task:

```text
Correct only the confirmed title in src/data/sample-lessons.json.
Do not change IDs, structure, or other lesson text.
Show the diff afterward.
```

Choose the boundary.

You probably need:

```text
READ      yes
WRITE     yes
EXECUTE   maybe, depending on verification
NETWORK   no
```

Now apply the project rule:

```text
Treat src/data/sample-lessons.json as authored content.
```

Does that mean the file can never change?

No.

It means the change deserves an explicit task and review. "Authored" is not the same as "immutable."

The task names the file and the intended content change, so a write can be justified.

But if the agent proposes rewriting both sample lessons "for consistency," the task has expanded.

That is where the stop condition matters.

## Review test

Before you approve a permission, ask:

> If this action succeeds, what new thing becomes possible?

For read, new information becomes visible.

For write, project state can change.

For execute, a program or project script can act.

For network, the session can cross the local boundary.

That is a better question than "Is this permission dangerous?"

Permissions are contextual. The task determines whether the capability is justified.

## Safety note

Do not practice permission decisions with real student records, school credentials, production systems, or private data you do not need for the lesson.

Synthetic repositories are not childish training wheels. They let you learn the control model without making privacy mistakes part of the learning process.
